30 秒讀懂：
  1. 系統只有兩種模式，啟動時用一個設定值選：vendor（廠商直接給語音＋情緒字串，同程序入列，不跑 ASR／LLM／TTS／BERT）、full（使用者開口說話，跑完整管線）。
  2. 兩種模式的後段完全相同：換臉 → Wav2Lip → WebRTC → 瀏覽器。
  3. full 模式的重點：回覆文字同時送 TTS 與 BERT；第一塊音訊到時，BERT 已有結果就用，沒有就用預設（中性），絕不等它。
  4. 圖上三種線：黑＝音訊、紫＝情緒控制、綠虛線＝狀態回報。粗線是跨程序，細線是同程序。
  5. 協定只有一處和早期不同：BERT 與用戶端之間由 HTTP 改 UDP；其餘沿用早期設計。

TCP 分幀：framed_client ⇄ framed_receiver

幀 type名稱方向內容 (payload)識別碼
1BEGINframed_client → framed_receiverJSON：{session, utterance, voice, sample_rate=16000, emotion, text}。emotion 值＝廠商字串（早期為整數 code；改字串好讓兩種模式共用 face_switcher，待確認）session＝LiveTalking 工作階段；utterance＝這一句的 id
2AUDIOframed_client → framed_receiverPCM16 LE 單聲道 16 kHz 原始位元組（大小不固定）。seq（遞增整數，用於偵錯亂序／漏幀）是新增設計，早期協定沒有，待確認；TCP 本身已保證順序歸屬「最近一個 BEGIN」的 utterance
3ENDframed_client → framed_receiver空。代表音訊送完，不代表播完；接收端收到 END 後補尾幀、標記 status=end歸屬同一個 utterance
4STATUSframed_receiver → framed_clientJSON：{utterance, state}。早期只有一次「整句畫完」；新版回報 playback_started／playback_ended 兩個事件（新增，欄位待確認）utterance 對應 BEGIN 的 id
  • 幀格式（沿用早期 joygen_client）：type 1B｜length 4B（大端）｜payload。
  • 「單一連線」的範圍：一個 imood-pipeline 程序對一個 LiveTalking 程序維持一條長連線，連線上依序傳多句話（BEGIN→AUDIO×N→END，下一句的 BEGIN 在上一句 END 之後）；不是一句話一條連線，也不是音訊／狀態各開一條。同一條連線反方向承載 STATUS。
  • 待確認：上一句尚未播完時下一句 BEGIN 可否先送（接收端依序入列即可）；使用者打斷（abort）時怎麼通知接收端清佇列。
  • vendor 模式完全不使用此 TCP 連線：接收端與 LiveTalking 同程序，直接入列。
